# Migration Rules

1. Every table ships with RLS ENABLED + explicit per-operation policies + explicit GRANTs in the SAME migration (CI-enforced by scripts/check-migrations.sh).
2. Append-only: never edit, rename, or delete an existing migration; corrections are new migrations. Additive-first: destructive changes require an explicit task instruction with operator approval.
3. Personal-data tables include home_country_code. Timestamps: timestamptz (UTC). Money: integer minor units or numeric, never floats.
4. Application: Lovable's Supabase integration writes AND applies each migration to ethio-prod in the same action. A migration is not DONE until read-back query evidence (table, RLS flag, policies, seeds) is produced from the live database. Committed-but-unapplied is a named deferral, never a silent pass.
5. Seeds in migrations: reference data only (e.g., countries). User/personal data is never seeded.
6. Environment note (standing): ethio-prod currently doubles as the development database pre-launch. A separate dev/preview database is a NAMED LAUNCH-GATE item before real users exist.
7. Generated artifacts (src/integrations/supabase/types.ts) refresh after schema changes; they are never hand-edited (Knowledge E5).
8. Every migration SELF-MARKS: its LAST statement is `INSERT INTO public.migration_marks(version) VALUES ('<a 14-digit version>') ON CONFLICT DO NOTHING;`. The SQL editor writes no ledger, so the mark IS the ledger on staging (and is identical on prod). CI-enforced by scripts/check-migrations.sh for every migration with version >= 20260817054246; `public.migration_marks` is RLS-enabled with an explicit deny-all policy for client roles and is readable only by `service_role` and the definer `public.e2e_migration_ledger()`.
9. DECLARED-MARK LAW (INC-094, 2026-08-29): the declared mark is NOT required to equal the file's own filename stamp. The migration tool assigns that stamp when it WRITES the file — after the SQL was authored — and tool-managed migration files cannot be edited afterwards, so a migration can never contain its own filename stamp by construction. The law is: declare a 14-digit mark at or after the file's filename stamp (marks stay monotonic; no file recycles an older stamp), and the tooling reads the DECLARED literal out of the file — `scripts/check-migrations.sh` checks presence + monotonicity, `scripts/e2e-migration-preflight.ts` (`declaredMark()`) compares declared marks against the ledger. For a file explicitly named in `scripts/migration-mark-allowlist.txt`, parity also accepts that immutable file's filename stamp when its cited later healer inserted the stamp; arbitrary filename marks remain invalid. Corrective ledger migrations remain legal and append-only, but the recursion they used to cause is gone.

10. DEFINER/REVOKE PAIRING (DEC-022-B, 2026-08-31): A DEFINER function's REVOKE lives in the same file. When the authoring tool splits them, the follow-up lands in the SAME landing, the operator applies both in one step, and the earlier file is allowlisted with its closer cited — the allowlist is printed on every run; nothing is silently skipped. The allowlist is `scripts/migration-guard-allowlist.txt`, one entry per line: `<filename> | <reason> | <closing migration uuid-fragment>`; `scripts/check-migrations.sh` skips those files in the definer scan and prints them under "Definer guard: allowlisted files (each cites its closer)". Trigger helpers default to SECURITY INVOKER; DEFINER is for gated entry points only.

11. **PROOF READERS (INC-1052, DEC-341, 2026-11-04): a proof reads a STABLE reader's answer INTO a variable first, and the WHERE compares the variable; a STABLE function that RAISEs is never named beside a column inside a WHERE clause of a DO block.** The planner pre-evaluates a STABLE function with constant arguments for its selectivity estimate under the DO statement's snapshot — taken before the proof's own scratch rows existed — so a reader that raises on a missing row raises there (`tier_rank <> public.feed_tier_rank(v_l1)` raised "unknown tier" for a level the proof had just inserted; the write path was sound). `SELECT … INTO STRICT v_rank FROM … WHERE key = v_key;` then `tier_rank <> v_rank`; `v_base := public.baseline_level_key();` once. CI-enforced by `scripts/conformance/proof-readers.test.ts` (CF-PROOF-1) over every DO block of every migration; its allowlist is empty by design.

12. **CATALOG FACTS (INC-1054, DEC-341, 2026-11-04): a proof asserts catalog facts from catalog columns — `pg_trigger.tgtype` bits, `tgattr` → attnames, `tgfoid::regprocedure`, `tgenabled`; `pg_proc.provolatile` / `prosecdef` / `proconfig`; `pg_constraint.con*`; `pg_policies.qual` / `with_check` — never by LIKE on a `pg_get_*def` text; `pg_get_functiondef` is read for md5 body comparisons only.** A deparsed definition's spelling follows the session's `search_path` and the server's version (`pg_get_triggerdef` printed `EXECUTE FUNCTION level_ranks_rebuild()`, unqualified, where the proof expected `public.level_ranks_rebuild()`; the trigger was right, the check was wrong). CI-enforced by `scripts/conformance/proof-readers.test.ts` (CF-PROOF-2, PRF-5) over every DO block of every migration stamped `20261104000000` or later — a `pg_get_(trigger|index|constraint)def(` followed by `LIKE` / `NOT LIKE`: directly, after a parenthesis enclosing it, or on the variable it was read `INTO`; three sites were fixed at landing (the fold `20261104153313`, `20261104124958`, `20261104153957`, none applied), and the two older sites (`20261014022725` :427, `20261014194317` :932) are applied history below the floor.

13. **LINE ENDINGS (INC-1056, 2026-11-05): a byte-comparison proof normalises line endings on both sides — `prosrc` AND each fragment or replacement literal through `replace(…, chr(13), '')` before it is counted, replaced or hashed.** A file carried by an operator's paste into the SQL editor arrives CRLF, so a literal spanning a line end holds chr(13) that the stripped `prosrc` does not: `20261104154000` (fbffa284) proof (b) answered "a staff-door fragment occurs 0 times" on ethio-staging while every CI lane, applying the same file by the CLI, passed. The ethio-prod applies are pastes. The three proofs of P-2 (a) that compare text against `prosrc` (`20261104124958`, `20261104154000`, `20261104154001`) were corrected in place before they landed on dev — proof text only, no schema statement, mark or grant changed.

14. **THE REFUSAL UNDER TEST (INC-1060, ruling 13, 2026-11-05): a refusal proof reads the door's refusal order and supplies arguments that pass every earlier check, so the answer it asserts can only come from the rule under test.** `edit_my_listing(…, '{}')` answers `nothing to change` (20261019115951 :124) before its status gate (:150–:152, `this listing is not edited`): a proof that sends an empty change set never reaches the gate, and asserting "anything but the gate's words" on the other side passes for the wrong reason. The proof names the rule it tests, lists the checks before it in the door's order with the argument that clears each (a title within the judge's limits, a seller who is active and within his dial, an ad that is his and in the status the gate reads), asserts the EXACT answer — the refusal's words and DETAIL, or, past the gate, what the door then does in the file's order (the judge's verdict, the certification, the UPDATE's columns, the revision) — and never a negation. The same law holds for a trigger under test: the row sent clears every constraint and every earlier trigger before the one it asserts.
